10. Active People

The right-side dashboard contains an:

14. B-4.9 Exit Detection

B-4.9 fixed an important edge case.

Previously, a person who simply disappeared from the current FrameResult did not necessarily generate a CUSTOMER_EXIT.

The current logic handles:

Person inside zone
       ↓
Track disappears
       ↓
Missing-track grace period
       ↓
Track genuinely lost
       ↓
CUSTOMER_EXIT

A grace period is used so a temporary tracker dropout does not immediately become a false exit.

The verified regression test covers:

Zone entry
Visible zone exit
Camera-sight disappearance
Grace-period protection
CUSTOMER_EXIT generation

All pass.

22. Runtime Integration

The main GUI starts the runtime in a worker thread.

The runtime startup flow is conceptually:

START RETAIL OS
      ↓
runtime_starting = True
      ↓
background worker
      ↓
RetailVisionRuntime()
      ↓
runtime.start()
      ↓
GUI receives runtime state

This prevents runtime startup from blocking the Tkinter event loop.

The current GUI then polls runtime state using Tkinter's scheduled callbacks.

32. Important Stability Decisions

Several GUI stability issues were deliberately fixed.

Dashboard throttling

The camera can update continuously while the human-facing dashboard updates at a lower rate.

Stable active-person rows

Rows are reused instead of recreated unnecessarily.

Persistent selected-person card

The selected-person detail card is updated in place.

Event processing

Event ingestion is separated from the visual dashboard refresh throttle so frame-level entry/exit events are not silently lost.

Tracker-loss grace period

A short grace period prevents temporary tracking loss from becoming an immediate exit.
